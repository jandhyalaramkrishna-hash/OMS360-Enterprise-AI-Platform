See `ai/providers/README.md`, `ai/rag/README.md`, `ai/mcp/README.md`, `ai/agents/README.md`, `ai/evals/README.md`, and `ai/integration/README.md` for each module.

## Purpose

This package is the isolated home for the AI infrastructure named in the project roadmap: RAG (Retrieval-Augmented Generation), MCP (Model Context Protocol) tool-calling, multi-agent orchestration, AI Evals, and — as of Sprint 2 — a runtime layer that can select and health-check a real LLM provider once one is wired up. As of Sprint 9, it also has a unified integration layer proving those pieces work together end to end. It exists so that when a real AI feature (starting with the already-documented AI Customer Support Chatbot, see `docs/architecture/`, `docs/business/`, `docs/qa/`) is built, it has clean, tested, production-quality primitives to build on rather than starting from nothing.

## Isolation guarantee

- `ai/` depends inward on `app/` — it reuses `app.database.get_db`-style DI patterns, `app.core.exceptions.OMSBusinessError`, and `app.core.logging_config.get_logger`.
- `app/api/ai/` (Sprint 3, extended Sprint 9) is the **one, narrow, explicitly-approved exception**: it imports from `ai/` to expose seven endpoints (six read-only from Sprint 3, plus Sprint 9's `GET /platform/health`). No other file under `app/` imports from `ai/`. `ai/services/chat_service.py`, `ai/providers/health.py`, `ai/rag/search_service.py`, `ai/mcp/server.py`, `ai/agents/agent_service.py`, `ai/evals/evaluation_service.py`, and Sprint 9's `ai/integration/workflow_service.py` are all built and unit-tested but not reachable from any HTTP endpoint yet — only `ai/integration/health.py`'s `PlatformHealthChecker` is, via the one new Sprint 9 route.
- `ai/config.py` is the only file that imports `app.config` directly. `ai/runtime/config.py` (Sprint 2) does not import `app.config` at all — it reads its own environment variables directly (see Feature Flags below), keeping the Sprint 2 runtime layer self-contained even from `ai/config.py`. `ai/rag/config.py` (Sprint 5) and `ai/mcp/config.py` (Sprint 6) follow the same self-containment pattern, independent of both and of each other. Sprint 9's `ai/integration/` introduces no new configuration surface of its own.
- No provider makes a real network/SDK call, no retriever reaches a real vector store, no MCP tool reaches a database, Kafka, or an external API, no agent is driven by a real AI model, and no evaluation calls a real LLM or external evaluation service. No Docker/Kafka/database change has ever been made from this package. `ai/` beyond `app/api/ai/` remains fully importable and unit-testable with zero effect on the running application until a future, explicitly-approved *new version* wires more of it in (e.g. a chat endpoint calling `AIChatService`, a search endpoint calling `RAGSearchService`, a tool-call endpoint calling `MCPServer`, an agent-run endpoint calling `AgentService`, an eval-run endpoint calling `EvaluationService`, or a workflow-run endpoint calling `AIWorkflowService`).

## Feature flags — two surfaces, by design

There are intentionally **two** flag systems, serving different consumers:

1. **Sprint 1 (`ai/config.py`)** — `AI_FEATURE_FLAGS` dict (`rag_enabled`, `mcp_enabled`, `agents_enabled`, `evals_enabled`, `prompts_enabled`), gated by `app/config.py`'s existing `FEATURE_FLAGS["ai_features_enabled"]` master switch. Used by `ai.dependencies.require_ai_enabled(...)`. Unchanged since Sprint 1 — kept for full backward compatibility.
2. **Sprint 2 (`ai/runtime/config.py`)** — environment variables `AI_ENABLED`, `RAG_ENABLED`, `MCP_ENABLED`, `AGENTS_ENABLED`, `EVALS_ENABLED`, read directly via `os.environ` (through `python-dotenv`, already an existing dependency), independent of `app/config.py`. Used by `AIService`, `ProviderRegistry`, `AIHealthService`, everything built in Sprint 2's AI Runtime Infrastructure, and — as of Sprint 9 — `AIWorkflowService`, indirectly, through each step's own existing gate.

Both default to fully disabled (fail-closed). This split was a deliberate Sprint 2 design decision, not an oversight — see `docs/governance/DECISION-LOG.md` DEC-0014 for the reasoning and the note that a future sprint may want to consolidate the two once it's clear which consumers (DI-gated capability checks vs. the runtime/provider layer) actually need which. Sprint 9 adds no new flag of its own — `AIWorkflowService.run()` adds zero enablement checks; each step enforces its own existing gate.

## Providers (Sprint 2 prepared, Sprint 4 adds a real one) — see `ai/providers/README.md`

`ai/providers/` has four Sprint 2 adapters (`OpenAIProvider`, `AnthropicProvider`, `AzureOpenAIProvider`, `OllamaProvider`), each correctly reporting `is_configured()` from its own environment variables (e.g. `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `AZURE_OPENAI_API_KEY`/`AZURE_OPENAI_ENDPOINT`, `OLLAMA_BASE_URL`). None of their `complete()` methods make a network call or import an LLM SDK — each deliberately raises `AIProviderNotConfiguredError` with a message explaining it is prepared but not yet wired for real calls. No LLM SDK dependency has been added to `requirements.txt`, since none is used yet.

Sprint 4 adds a fifth provider, `MockAIProvider` ("mock") — the only one whose `complete()` actually runs, entirely in-process, no network call or credential. `ProviderFactory` (`ai/providers/factory.py`) now owns construction of all five; `ai.services.factory.ServiceFactory.build_provider_registry()` delegates to it. `AIChatService` (`ai/services/chat_service.py`) is the first service that calls a provider through this registry and gets back a real result — and, as of Sprint 9, the step `AIWorkflowService` uses for both its chat step and its evaluation step. Full detail: `ai/providers/README.md`.

## MCP tool-calling (Sprint 1 prepared, Sprint 6 adds four real mock tools) — see `ai/mcp/README.md`

`ai/mcp/` has the `MCPTool` interface and `MCPToolRegistry` from Sprint 1, unchanged. Sprint 6 adds `MCPRequestRouter` (method dispatch + request validation, enforcing a per-call timeout), `MCPServer` (the capability-gated, ergonomic entry point — `list_tools()`/`call_tool()`), `MCPHealthChecker` (a live probe, mirroring `ProviderHealthChecker`'s role), and four deterministic mock tools (`order_lookup`, `inventory_lookup`, `delivery_status_lookup`, `kitchen_status_lookup`), registered via `MCPToolFactory` into the *same* shared `MCPToolRegistry` singleton Sprint 1 built — not a second, MCP-server-only registry, the same "one shared registry" choice Sprint 4 made for providers. Full detail: `ai/mcp/README.md`.

## Multi-agent orchestration (Sprint 1 prepared, Sprint 7 adds six real mock agents, Sprint 9 adds one passthrough) — see `ai/agents/README.md`

`ai/agents/` has the `AgentBase` interface and `AgentOrchestrator` from Sprint 1; Sprint 7 extracts the orchestrator's previously-internal agent dict into its own `AgentRegistry` (composed, not duplicated — the orchestrator still works with zero constructor arguments) and adds `AgentMessageBus` (mock agent-to-agent messaging, recorded directly on `AgentContext.messages`), `AgentHealthChecker` (a live probe, mirroring `MCPHealthChecker`'s role), `AgentService` (the capability-gated, ergonomic entry point — `run(agent_names, context)`/`list_agents()`), and six deterministic mock agents (Order, Inventory, Kitchen, Delivery, Customer Support, Analytics), registered via `AgentFactory` into the *same* shared `AgentOrchestrator` singleton Sprint 1 built. Sprint 9 adds one further additive method, `AgentOrchestrator.get_agent(name)`, so `PlatformHealthChecker` can fetch agent objects for its live probes. Full detail: `ai/agents/README.md`.

## Evaluation (Sprint 1 prepared, Sprint 8 adds accuracy/latency scoring and a real mock target) — see `ai/evals/README.md`

`ai/evals/` has `EvalCase`/`EvalResult`/`EvalReport` and `EvalRunner` from Sprint 1; Sprint 8 adds `response_evaluator.py` (comparator functions), `AccuracyScorer`, `LatencyAnalyzer` (reads a new `EvalResult.execution_time_ms` field `EvalRunner` now populates), `EvaluationReportBuilder` (combines both into an `EvaluationSummary`), `MockEvalDataset` (six built-in cases), `PromptEvaluator` (runs cases through the *existing* Sprint 4 `MockAIProvider`, not a second mock provider), and `EvaluationService` (the capability-gated, ergonomic entry point — `evaluate(cases, target)`). As of Sprint 9, `AIWorkflowService` runs this same `MockEvalDataset` through the same chat call path its own workflow just used, as the final step of the unified workflow. Full detail: `ai/evals/README.md`.

## Enterprise Integration — Unified AI Workflow (Sprint 9) — see `ai/integration/README.md`

`ai/integration/` is new this sprint: `AIWorkflowService.run(order_id, query=None)` chains all five modules above into one call — `RAGSearchService.search()` → `MCPServer.call_tool("order_lookup", ...)` → `AgentService.run()` (all six mock agents) → `AIChatService.send_message()` (seeded with the RAG context) → `EvaluationService.evaluate()` (the built-in mock dataset, scored through the same chat call the workflow itself just made). `PlatformHealthChecker.check()` aggregates `AIHealthService`, `ProviderHealthChecker`, `MCPHealthChecker`, `AgentHealthChecker`, and an `AIMetrics` snapshot into one unified report — reachable both via dependency injection and, uniquely among this sprint's additions, via the one new HTTP route, `GET /api/v1/ai/platform/health`. Neither collaborator introduces any new retrieval, tool-call, agent-run, evaluation, or provider-call logic, nor any new capability-gating mechanism — every step reuses its module's own existing, unmodified service and gate. Full detail: `ai/integration/README.md`.

## Structured logging

Every module in this package — Sprint 1 through Sprint 9 alike — logs through the existing `app.core.logging_config.get_logger(...)`, so AI-layer log lines are automatically JSON-formatted with the same `request_id`/`environment`/`hostname` context as the rest of the app. Logger names are namespaced per submodule (`ai.rag`, `ai.mcp.*`, `ai.agents.*`, `ai.evals`, `ai.evals.*`, `ai.prompts`, `ai.dependencies`, `ai.runtime`, `ai.providers.*`, `ai.services.*`, `ai.metrics`, `ai.integration.*`) so AI-layer logs can be filtered independently of OMS360 business-logic logs.

## Tests

`tests/ai/` mirrors this package's structure (Sprint 1 through 9 tests side by side); `tests/api/ai/` covers the API route layer separately (Sprint 3's six routes plus Sprint 9's one); `tests/integration/` (new in Sprint 9) holds true end-to-end tests that assemble the full production-shaped wiring (every real provider, all four real MCP tools, all six real mock agents, the real built-in RAG documents and eval dataset) rather than a minimal per-module fixture. Tests use `asyncio.run(...)` inside plain `def test_...()` functions rather than `async def test_...()`, so they run correctly under the existing `pytest` in `requirements.txt` without adding a new dependency (`pytest-asyncio` is not installed). Env-var-dependent tests use pytest's built-in `monkeypatch` fixture, so they don't depend on (or pollute) the real process environment or any `.env` file.

## How this gets wired in further (not done through v1.0.0)

Sprint 3 wired the read-only status/config/providers/features/metrics/health endpoints into `app/main.py`; Sprint 9 additionally wired the unified platform-health endpoint. Development on this line is now closed at v1.0.0 (see `docs/release/SPRINT-LOG.md`, `docs/governance/MASTER-PROJECT-MEMORY.md`). Should a future, separately-scoped version be started, candidates already identified across Sprints 3–9 include: a chat endpoint (`POST /api/v1/ai/chat`, backed by `AIChatService.send_message()`), a search endpoint (`POST /api/v1/ai/search`, backed by `RAGSearchService.search()`), MCP tool-listing/tool-call endpoints (backed by `MCPServer.list_tools()`/`call_tool()`), an agent-run endpoint (backed by `AgentService.run()`), an eval-run endpoint (backed by `EvaluationService.evaluate()`), a workflow-run endpoint (backed by Sprint 9's `AIWorkflowService.run()`), a provider-health endpoint backed by `ProviderHealthChecker`, and/or actually implementing a real vendor adapter, vector-store-backed retriever, real MCP client/transport, real AI-model-driven agent, or real LLM evaluation service (explicitly out of scope for all of Sprints 1–9). Until then, `AIChatService`, `ProviderHealthChecker`, `RAGSearchService`, `MCPServer`, `AgentService`, `EvaluationService`, and `AIWorkflowService` remain reachable only via `ai.dependencies.get_chat_service()` / `get_provider_health_checker()` / `get_search_service()` / `get_mcp_server()` / `get_agent_service()` / `get_evaluation_service()` / `get_ai_workflow_service()` and direct unit/integration tests — no HTTP client can reach them yet, except `PlatformHealthChecker` via `GET /api/v1/ai/platform/health`.
